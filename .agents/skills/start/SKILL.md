# start — 티켓 작업 시작

입력: Jira 이슈 키(예: `SCRUM-12`). 없으면 묻는다.

## 순서

1. **작업 트리 확인**: `git status`로 커밋 안 된 변경이 있는지 본다. 있으면 멈추고 어떻게 할지 묻는다.
2. **티켓 읽기**: Jira 도구로 이슈의 제목, 설명, 완료 조건, 컴포넌트, 담당자를 읽는다. 담당자가 다른 사람이면 진행 전에 확인한다.
3. **맥락 읽기**: 티켓이 가리키는 `specs/<기능>/spec.md`와 `plan.md`, 관련 API가 있으면 `docs/api/openapi.yaml`, 해당 영역의 `AGENTS.md`를 읽는다.
4. **브랜치 만들기**: 로컬이나 원격(`git fetch`)에 같은 이슈 키의 브랜치가 이미 있으면(예: `spec` 스킬이 스펙 문서를 커밋해 둔 첫 태스크 브랜치) 그 브랜치로 전환해 이어서 작업한다. 없으면 `main`을 최신으로 받은 뒤 `<type>/<이슈키>-<영문-설명>` 브랜치를 만든다(예: `feat/SCRUM-12-login`). type은 티켓 성격에 맞춘다.
5. **티켓 상태 전환**: Jira 도구로 이슈를 In Progress로 옮기고, 담당자가 비어 있으면 현재 사용자로 지정한다.
6. **구현 계획 제시**: 바꿀 파일, 추가할 테스트, 완료 조건을 어떻게 확인할지를 짧게 제시한다. 스펙과 티켓이 어긋나거나 불명확한 점이 있으면 여기서 묻는다.
7. **승인 후 구현**: 사람이 계획을 승인하면 구현한다. 승인 전에는 코드를 고치지 않는다.

## 규칙

- 티켓 범위 밖의 수정은 하지 않는다. 발견한 문제는 새 티켓으로 제안한다.
- API 변경이 필요한데 티켓에 없으면 멈추고 백엔드 담당과 합의하도록 안내한다.
- 커밋 메시지는 `<type>(<이슈키>): 설명` 형식이다.

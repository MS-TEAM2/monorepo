# spec — 기획을 스펙·티켓으로 (간소화 흐름)

입력: Notion 기획 목록의 **기능 행 링크**. 없으면 무엇을 만들지 한 번 묻는다.

별도의 스펙 PR은 만들지 않는다. 승인은 4단계에서 **한 번**만 받고, 스펙 문서는 첫 태스크 PR에 함께 들어간다.

## 순서

1. **기획 읽기**: Notion 도구로 기획 행을 읽는다. 문제, 대상 사용자, 성공 기준이 빠져 있으면 지어내지 말고 사용자에게 묻는다. 같은 기능의 `specs/<기능>/`이 이미 있으면 새로 만들지 않고 고친다.
2. **기능 이름 정하기**: 영문 소문자와 하이픈으로 짧게 정한다(예: `login`, `model-serving`). 폴더는 `specs/<기능>/`.
3. **문서 3개 작성**: `specs/_template/`의 세 파일을 복사해 채운다.
   - `spec.md`: 무엇을·왜만. 구현 방법은 적지 않는다. 불확실한 부분은 `[확인 필요: 질문]`.
   - `plan.md`: 영역(FE/BE/AI)별 변경, API 변경, 데이터·모델, 위험. 변경이 없는 영역은 "없음". API가 바뀌면 `docs/api/openapi.yaml` 변경을 포함한다.
   - `tasks.md`: 태스크 하나는 한 사람이 하루 안팎에 끝낼 크기, 한 영역에만 속하게. API 명세 태스크를 맨 앞에 둔다. 각 태스크에 완료 조건을 붙인다.
4. **한 번에 확인받기 (여기서 멈춘다)**: 아래를 한 화면에 정리해 보여 주고 승인을 받는다. PM과 해당 영역 리드가 함께 보도록 안내한다(통화 또는 Slack 스레드). 고칠 점을 반영해 다시 보여 주고, 승인 전에는 다음 단계로 가지 않는다.
   - spec.md 요약 (문제 · 요구사항 · 범위 밖 · 성공 기준 · 확인 필요)
   - plan.md의 영역별 변경 표
   - 만들 Jira 이슈 목록: 에픽 1개 + 태스크별 이슈(`ticket` 스킬의 이슈 양식을 따른다). 담당자는 사용자가 지정한 경우에만 넣는다.
5. **Jira 생성**: 승인되면 Jira 도구로 에픽을 만들고, 태스크 이슈를 만들어 에픽에 연결한다. 유형은 기능이면 Story, 그 외는 Task. 컴포넌트는 `FE` / `BE` / `AI`. 태스크 이슈는 진행 중인 스프린트에 넣어 보드에 바로 보이게 한다(에픽은 넣지 않는다). 진행 중인 스프린트가 없으면 백로그에 만들고 그 사실을 알려 준다. 같은 제목의 열린 이슈가 있으면 새로 만들지 않고 알려 준다.
6. **기록**:
   - `tasks.md` 각 태스크 앞에 이슈 키를 적는다(예: `- [ ] SCRUM-11 [BE] 로그인 API 명세 추가`).
   - Notion 기획 행의 `Jira 에픽`에 에픽 키를 적고 `상태`를 `스펙 승인`으로 바꾼다.
7. **첫 태스크 브랜치에 커밋**: `main`을 최신으로 받은 뒤 `tasks.md` **맨 앞 태스크**의 키로 브랜치를 만든다(예: `feat/SCRUM-11-login-api-spec`). `specs/<기능>/` 세 파일만 `docs(<첫 태스크 키>): <기능> 스펙 추가`로 커밋하고, 사용자 확인을 받아 push 한다.
8. **안내**: 만든 에픽·이슈 키와 링크, 그리고 다음 할 일을 알려 준다.
   - 첫 태스크 담당: `start <첫 태스크 키>` (같은 브랜치에서 이어서 작업, 스펙 문서가 이 PR에 함께 들어간다)
   - 나머지 담당: 선행 태스크가 머지되면 `start <키>`

## 규칙

- 문서는 짧게. 템플릿에 없는 섹션을 늘리지 않는다.
- 받지 않은 수치·일정·요구사항을 지어내지 않는다.
- 4단계 승인 전에는 Jira·Notion·Git에 아무것도 쓰지 않는다.
- Jira 호출은 필요한 만큼만 한다(무료 플랜 한도는 사이트당 시간당 500회).

# pr — 셀프 리뷰 후 PR 생성

## 순서

1. **브랜치 확인**: 브랜치 이름에서 이슈 키를 뽑는다(`feat/SCRUM-12-login` → `SCRUM-12`). `main`이거나 키가 없으면 멈춘다.
2. **셀프 리뷰**: `main` 대비 전체 변경을 읽고 아래를 점검한다. 문제가 있으면 고치거나 사용자에게 알린다.
   - 티켓의 완료 조건을 모두 충족하는가
   - 티켓 범위 밖의 변경이 섞이지 않았는가
   - 비밀 값, 개인정보, 디버그 코드, 주석 처리된 코드가 없는가
   - 바뀐 동작에 테스트가 있는가
   - API를 바꿨다면 `docs/api/openapi.yaml`과 프론트 타입(`gen:api`)이 갱신됐는가
   - 화면을 바꿨다면 휴대폰 폭에서도 깨지지 않는가 (앱이 같은 화면을 띄운다)
   - `packages/bridge`를 바꿨다면 웹·앱 양쪽이 함께 고쳐졌고 기존 요청이 그대로 동작하는가
   - 해당 영역 `AGENTS.md` 규칙을 지켰는가
3. **검사 실행**: `pnpm check`를 돌린다. 실패하면 고치고 다시 돌린다. 통과하지 못하면 PR을 만들지 않는다.
4. **커밋·푸시**: 남은 변경을 `<type>(<이슈키>): 설명` 형식으로 커밋하고 브랜치를 push 한다.
5. **PR 생성**: GitHub 도구(`gh pr create`)로 PR을 만든다. 제목은 `[<이슈키>] 설명`, 본문은 `.github/pull_request_template.md` 양식을 채운다. "변경 요약"은 사용자가 이해하고 설명할 수 있는 내용으로 쓰고, 초안을 사용자에게 확인받는다.
6. **티켓 상태 전환**: Jira 도구로 이슈를 In Review로 옮기고 PR 링크를 댓글로 남긴다.
7. **마무리**: PR 링크와, 프론트 변경이 있으면 미리보기 URL이 PR 댓글로 달린다는 점을 알려 준다. `mobile/`의 네이티브 부분을 바꿨다면 머지 후 `mobile-build` 워크플로로 앱을 다시 빌드해야 한다고 알려 준다.

## 규칙

- 검사를 건너뛰거나 훅을 우회하지 않는다.
- PR 하나는 티켓 하나다. 리뷰어가 30분 안에 읽을 수 있는 크기가 아니면 나누자고 제안한다.
- 머지는 사람이 한다. 머지 후 티켓을 Done으로 옮기는 것은 머지한 사람이 요청할 때 Jira 도구로 처리한다.

## 1. 라벨 결과

### 만드는 방법

```bash
uv run python -m ai_core.survival.labels --csv-dir <인허가 3종 CSV 폴더> --geojson <행정동 경계 GeoJSON> --out <새 폴더>
```

- 입력:
  - 열린데이터광장 인허가 3종 CSV(일반음식점, 휴게음식점, 제과점). 파일 이름은 `ai_core/ingest/licenses.py`의 `SOURCES`에 있다.
  - 행정동 경계: vuski/admdongkor `ver20261001`
- 출력: `survival_labels.csv`(라벨), `label_report.json`(건수 보고). `--out`에 파일이 이미 있으면 덮어쓰지 않고 멈춘다.
- 걸리는 시간: 전체 데이터 기준 약 2분 30초(팝업 업체 판정이 대부분)
- 코드: `ai/src/ai_core/survival/labels.py`의 `build_labels()`(라벨)와 `label_report()`(보고)

### 저장 위치

- 지금은 각자 로컬에서 만든 파일뿐이다. `ai/AGENTS.md`에 따라 레포에는 커밋하지 않는다.
- 팀이 함께 쓸 저장 위치(Blob Storage 경로 또는 DB 테이블)는 **[확인 필요]** 상태다. 정해질 때까지는 위 명령으로 각자 다시 만든다.

## 2. 라벨 규칙과 이유

| 규칙 | 이유 |
| --- | --- |
| 영업 중이면 원천별 관측 종료일까지를 기간으로 보고 중도절단한다. 2025년에서 자르지 않는다 | Notion 6장. 최근 개업도 관측된 만큼 쓴다 |
| 관측 종료일 뒤의 폐업일은 중도절단으로 본다 | 원천마다 갱신일이 달라 미래 날짜가 섞일 수 있다 |
| 영업 중인데 관측이 12개월보다 짧으면 12개월 표본에서 뺀다(`not_observed_12m`) | 아직 모르는 결과를 폐업으로 보지 않는다 |
| 12개월 안 폐업 판정은 `closed_on < licensed_on + 12개월`로 한다 | 이전 분석과 같은 기준 |
| 공통 제외: 대상이 아닌 업태, 인허가일 없음, 날짜 역전, 미분류, `한시적` 상호, 폐업인데 폐업일 없음 | Notion 6장과 SCRUM-99 업종 규칙 |
| 12개월 모델만 추가로 제외: 확정 팝업, 좌표 없음, 면적 0·결측 | Notion 6장. Kaplan-Meier에는 적용하지 않는다 |
| 제외 사유는 위 순서에서 처음 걸린 것 하나만 기록한다 | 건수가 겹치지 않게 |

### 팝업 (2026-11-26 상기님 결정, 기획서 100m 규칙 대신)

- 개업 시점에 알 수 있는 정보로만 판정한다. "60일 안에 폐업"처럼 폐업한 뒤에야 알 수 있는 기준으로 빼면, 빨리 망한 일반 매장까지 빠져서 생존율이 부풀려진다.
- **확정(12개월 표본에서 제외):**
  - ① 상호에 `한시적` 또는 `(한시)`
  - ② 주소가 행사장·팝업·부스·특설·일대·일원 등 임시 장소
  - ③ 팝업 업체: 같은 핵심 상호로 직전 1년에 인허가 3건 이상이고, 그 과거 건의 영업일 중앙값이 60일 이하. 개업일 전에 이미 끝난 과거 건만 본다.
- **의심(표시만):** ④ 같은 주소에서 직전 1년에 개업 3건 이상(`popup_suspect`)
- ⑤ 100m 안 같은 업종이 1년에 10곳 이상 개업(기획서 규칙)은 번화가의 일반 매장을 많이 잡아서 제외 기준으로 쓰지 않는다. 피처 계산은 SCRUM-118에서 한다.
- Notion 데이터 전처리와 `plan.md`에는 아직 100m 규칙이 적혀 있어 고쳐야 한다. **[확인 필요: 문서 수정 담당]**

### 다시 개업 의심

- 같은 주소(호실 포함, 공백 제거)에서 상호까지 같은데, 폐업 후 0–90일 안에 새 인허가가 난 경우다. 앞 인허가에 `reopen_suspect`로 표시하고 **합치지 않는다.**
- 상호가 바뀐 재등록(예: 직영점 전환)은 폐업 1건과 새 개업 1건으로 본다(2026-11-26 결정). 서비스가 보여 주는 생존확률은 "그 자리나 브랜드가 남는가"가 아니라 "그 사업자가 버티는가"이기 때문이다.

## 4. 모델링에 영향을 줄 발견과 주의할 점

1. **Kaplan-Meier에 확정 팝업이 들어 있다.** Notion은 Kaplan-Meier에 팝업 조건을 적용하지 않는다고 정했다. 그런데 팝업을 빼면 12개월 값이 크게 바뀐다(11/26 분석, 확정 팝업 ①②③ 기준).
   - 제과점: 0.593 → 0.663 (3,318건 중 413건이 팝업)
   - 호프·치킨: 0.818 → 0.869
   - 분식: 0.789 → 0.818
   - 한식·카페: +1.5%p

   12개월 모델은 팝업을 빼고 학습하는데 기준선은 팝업을 포함하면, SCRUM-119의 Brier 비교가 같은 모집단끼리의 비교가 되지 않는다. **[확인 필요: 기준선에서도 확정 팝업을 뺄지]**
2. **미분류 매장은 더 빨리 망한다.** 2023–25년 개업(확정 팝업 제외) 기준이다.

   | | n | 12개월 안 폐업 | 30일 안 폐업 | KM 12m |
   | --- | --- | --- | --- | --- |
   | 분류됨 | 43,002 | 15.5% | 4.8% | 0.845 |
   | 미분류 | 12,419 | 27.5% | 16.5% | 0.725 |

   미분류를 빼서 생존율이 조금 높게 나올 수 있다(전체 0.818 vs 분류됨 0.845). 화면 한계 문구에 반영할지 검토한다.
3. **업종 매핑률:** 2023–25년 개업 기준 77.6%(확정 팝업 제외)로 기획서 통과 기준 90%에 못 미친다. 현재 영업 매장은 인허가만으로 85.6%다.
4. **표본이 작은 업종:** 36개월 위험 집합이 fastfood 184, chinese 314, bakery 415다. 범위가 넓게 나올 수 있어 최소 표본 기준이 필요하다(`spec.md` 확인 필요 항목).
5. **누수:** 팝업 ③과 ④는 개업일보다 앞선 인허가만 본다. 재개업 의심은 뒤 인허가를 보고 앞 건에 표시하므로 **피처로 쓰면 안 된다**(분석·비교용).
6. **원천마다 관측 종료일이 다르다**(최대 18일 차이). 연도 순서로 검증할 때 원천을 섞어도 되는지 확인이 필요하다.
7. `role_dev`·`role_final`은 `plan.md`의 검증 설계를 열로 옮긴 것이다. 2025년 시험은 한 번만 한다(`final_test_once`).

## 5. 117–120 관련해 이미 해 본 것

- **Kaplan-Meier:** 업종별 12·24·36개월 점 추정만 계산했다(3장, 4장 1번). 신뢰구간, 보정, 기준선 함수는 하지 않았다.
- **다시 개업을 합친 경우:** 11/26에 같은 상호(A)와 핵심 상호(B) 재등록을 한 매장으로 이어 붙여 Kaplan-Meier를 다시 계산해 봤다. B를 합치지 않기로 결정해서 채택하지 않았다. 그때의 수치는 저장해 두지 않았다. **[확인 필요]**
- **모델(로지스틱, LightGBM), 보정, 요인 설명, 추론 연결:** 이 세션에서는 시도하지 않았다. 다른 사람이 해 본 것이 있는지는 **[확인 필요]**
- **추론 함수 계약:** SCRUM-115에서 `ai_core/survival/contract.py`와 `examples.py`에 정해져 있다. `nearby_open_1y_100m`(팝업성 위치 판정용 입력)은 4장의 팝업 결정과 맞지 않을 수 있다. **[확인 필요]**
